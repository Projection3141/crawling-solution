# Mall Collector

천유닷컴과 과자생각의 상품·가격·재고 상태·상세 정보를 수집하는 Windows 데스크톱 프로그램입니다. 두 사이트의 결과를 같은 상품 형식으로 정리하고, 기존 아카이브에 누적 갱신합니다. 1회 수집과 주기적인 반복 수집을 지원합니다.

## 1. 실행 및 준비

설치본은 설치 후 **Mall Collector**를 실행합니다. 소스 코드로 실행하려면 프로젝트 폴더에서 다음 명령을 사용합니다.

```powershell
npm install
npm start
```

`npm install` 과정에서 수집용 Chromium 브라우저도 설치합니다. 브라우저 설치가 누락된 경우 `node scripts/install-playwright.js`를 실행한 뒤 다시 시작합니다.

앱에서 다음 순서로 준비합니다.

1. 수집할 쇼핑몰의 계정을 등록하고 선택합니다.
2. OpenAI API 키를 등록하고 사용할 프로필을 선택합니다. 현재 화면에서는 일반·상세 수집 모두 프로필 선택이 필요하며, 새 번역 요청은 상세 수집에서 수행합니다.
3. 천유에서 프록시를 사용할 경우 등록된 프록시 프로필을 선택합니다. 과자생각은 직접 연결합니다.
4. 일반/상세 수집, 페이지 범위, 브라우저 표시 여부와 1회/반복 실행을 설정합니다.
5. 결과 저장 폴더를 확인한 뒤 실행합니다.

사이트 계정은 `.env`의 `ACCOUNT_ID`, `ACCOUNT_PW`로도 지정할 수 있습니다. 천유 프록시와 OpenAI API 키는 앱에서 등록·선택한 프로필을 사용합니다. 같은 사이트·계정의 수집과 장바구니 작업은 동시에 실행할 수 없습니다.

## 2. 수집 실행 시 공통으로 하는 작업

1. 선택한 계정·설정을 확인하고 수집용 브라우저를 실행합니다.
2. 사이트에 로그인한 뒤 지정한 범위의 상품 목록과 판매 상태를 읽습니다.
3. 선택한 수집 종류에 따라 재고·가격 또는 상세 정보를 수집합니다.
4. 사이트별 원본 데이터를 공통 상품 형식으로 변환합니다.
5. 기존 아카이브와 병합하고 이번에 수집한 소비자가·도매가를 각각 엔화로 환산한 뒤 실행별 JSON·CSV를 저장합니다. 관측하지 못한 가격으로 기존 유효 가격을 덮어쓰지 않습니다.
6. 실행 상태와 결과 파일을 화면에 표시하고 수집용 브라우저를 정리합니다.

천유는 수집 차수별로, 과자생각은 목록 페이지별로 일반 수집 데이터를 중간 저장합니다. 상세 데이터도 번역 요청 전에 먼저 저장하므로 번역 장애가 이미 확보한 가격·이미지를 잃게 하지 않습니다.

**서버 전송은 수집 완료와 별도입니다.** `수집정보 서버 전송`이 ON이면 앱의 전송 스케줄러가 통합 아카이브를 주기적으로 전송합니다. 수집 완료 표시만으로 서버 반영까지 완료됐다고 판단하지 말고 전송 내역을 확인해야 합니다.

## 3. 수집 종류별 데이터와 절차

### 일반 수집

가격과 판매·재고 상태를 자주 갱신할 때 사용합니다. 새 번역 요청은 하지 않으며 기존 번역값을 유지합니다.

| 사이트 | 수집·갱신하는 주요 데이터 | 간략한 절차 |
| --- | --- | --- |
| 천유 | 상품 ID·이름, 옵션 ID·이름, 구매 가능 수량, 판매·품절 상태, 낱개 도매가·소비자가 | 목록에서 소비자가 조회 → 옵션/장바구니 팝업 확인 → 필요한 상품의 장바구니 재고 보완 → 중간 저장·최종 병합 |
| 과자생각 | 상품 ID·이름, 판매가, 판매중/품절 상태 | 목록 페이지 조회 → 상품별 가격·판매 상태 판독 → 페이지별 저장 → 최종 병합 |

과자생각 일반 수집은 **정확한 재고 개수를 수집하지 않습니다.** `stockQuantity`가 `null`이어도 `saleStatus`, `stockStatus`로 판매·품절 상태를 확인할 수 있습니다.

천유 소비자가는 목록의 각 상품에 있는 `.m_pdt_list_icon .sale`에서 읽습니다. 예를 들어 `45,000원`은 `consumerPrice: 45000`으로 수집하고 `originalPrice`에 반영합니다. 소비자가 갱신을 위한 추가 상세페이지 요청은 없습니다. 소비자가를 읽지 못하면 경고를 표시하고 기존 소비자가와 엔화 환산값을 유지합니다.

### 상세 수집

일반 수집 과정을 거친 뒤 상품 상세페이지를 방문하여 정보를 보충합니다. 상세 저장 후 상품명은 일본어·영어, 옵션명은 일본어로 번역하며, 기존에 유효한 번역이 있으면 재사용합니다.

| 사이트 | 추가 수집하는 주요 데이터 | 간략한 절차 |
| --- | --- | --- |
| 천유 | 소비자가, 카테고리·브랜드 정보, 바코드, 소재·포장 크기·무게·원산지, 썸네일·메인·설명 이미지 | 일반 수집 → 상세 대상 선택 → 상세페이지 수집 → 저장 → 필요한 번역 → 최종 병합 |
| 과자생각 | 상세 판매가, 카테고리·브랜드 정보, 소비기한·낱개가·박스 구성·모델명·배송비 등의 스펙, 썸네일·메인·설명 이미지 | 일반 수집 → 범위 내 상세페이지 수집 → 저장 → 필요한 번역 → 최종 병합 |

천유 상세 모드는 두 가지입니다.

- **범위 내 전체 상품:** 해당 범위의 기존 상품도 다시 갱신합니다. 종료 페이지를 지정해야 하며 작업당 최대 20페이지입니다. 과자생각 상세도 이 방식을 사용합니다.
- **신규·상세 미수집 상품:** 천유에서만 사용할 수 있습니다. 새 상품·실패 상품·데이터 형식 변경으로 재확인이 필요한 상품을 수집합니다. 이미 성공한 상품을 매주 다시 갱신하는 용도에는 `범위 내 전체 상품`을 선택합니다.

### 가격·이미지 필드 읽는 법

| 필드 | 천유 | 과자생각 |
| --- | --- | --- |
| `originalPrice` | 목록의 소비자가. 목록값이 없고 상세 수집값이 있으면 상세페이지 소비자가로 보완 | 기존 판매가 |
| `wholesalePrice` | 일반 수집의 낱개 도매가 `onePrice` (팝업의 `inoPrice`, 장바구니의 `inOnePrice`) | `originalPrice`와 같은 판매가 |
| `currency` | `KRW` | `KRW` |
| `yenWholesalePrice` | 일반 수집에서 관측한 `wholesalePrice`의 엔화 환산값 | 일반·상세 수집에서 관측한 `wholesalePrice`의 엔화 환산값 |
| `yenOriginalsalePrice` | 일반·상세 수집에서 관측한 `originalPrice`의 엔화 환산값 | 일반·상세 수집에서 관측한 `originalPrice`의 엔화 환산값 |
| `createdAt` | 최초 수집 저장 시각(ISO 8601 UTC). 이후 유지 | 동일 |
| `updatedAt` | `createdAt`이 있는 상품을 다시 수집·저장한 시각. 최초 저장 시 `null` | 동일 |

예를 들어 천유 소비자가가 8,500원이고 낱개 도매가가 5,525원이면 `originalPrice: 8500`, `wholesalePrice: 5525`로 저장됩니다. `onePrice`에는 수량 할인 가격을 대신 넣지 않으며, 낱개 가격을 확인하지 못하면 기존 도매가를 유지합니다. 수량을 1로 바꾸어 재계산하던 `unitPriceAtOne`은 더 이상 수집하지 않습니다. 환율이 1원당 0.1엔이면 일반 수집에서 `yenWholesalePrice: 560`, `yenOriginalsalePrice: 850`으로 함께 저장합니다. 환산은 원화 × 환율을 10엔 단위로 올림합니다. 예를 들어 1,872엔은 1,880엔으로 저장하고, 이미 10엔 단위인 값은 유지합니다. 필드명은 `yenOriginalsalePrice` 철자를 그대로 사용합니다.

한 실행에서는 같은 환율 스냅샷을 사용하되, 이번에 관측한 가격만 환산합니다. 천유 일반 수집과 상세 모드의 선행 일반 수집에서 도매가와 소비자가를 함께 갱신합니다. 신규·상세 미수집 모드에서 상세 대상에서 제외된 기존 상품도 목록 소비자가로 갱신됩니다. 과자생각은 두 원화 가격이 같으므로 두 엔화 필드도 같은 값으로 갱신합니다.

환율 조회에 실패하면 원화값은 저장합니다. 원화 가격이 바뀐 항목의 과거 엔화 환산값만 `null`로 비우고, 바뀌지 않은 가격의 환산값은 유지합니다. 다음에 해당 가격을 관측하고 환율 조회에 성공하면 복구합니다. 두 엔화값이 반드시 같은 시점의 환율이라는 의미는 아닙니다. 기존 아카이브에 새 엔화 필드가 없으면 `null`로 시작하며 해당 가격의 다음 수집 때 채워집니다. 결과 JSON·아카이브에서 원화 두 필드와 엔화 두 필드를 짝지어 확인하세요.

`yenPrice`, `adminMemo`, `convertTime`은 상품 결과·아카이브·전송 필드에서 제거했습니다. 기존 `createdAt`은 유지합니다. `createdAt`이 없고 구버전 `convertTime`만 있으면 같은 시점의 ISO 형식으로 이전합니다. 예: 한국 시각 `2609081200` → `2026-09-08T03:00:00.000Z`. 이전 버전에 저장된 환산 시각으로 실제 최초 수집 시각을 복원할 수는 없으므로, 기존 값은 보존하고 이후 수집부터 `updatedAt`을 기록합니다.

수집 저장 시 `createdAt`이 없으면 해당 시각을 기록하고, 있으면 `createdAt`은 유지하면서 `updatedAt`을 갱신합니다. 환율 실패·가격 미관측·동일 데이터 재수집에도 적용하며 번역만 갱신할 때는 두 시각을 바꾸지 않습니다. 한 실행 안에서도 중간 저장 뒤 다시 저장하면 `updatedAt`이 생길 수 있습니다.

마지막 상품 수집 저장 시각은 `Date.parse(product.updatedAt || product.createdAt)`으로 비교할 수 있습니다. `null`·유효하지 않은 날짜는 미확인으로 처리해야 합니다. 이는 상품별 저장 시각이므로 전체 작업 완료나 마지막 상세 성공을 보장하지 않습니다. 현재 반복 실행은 작업 시작 기준의 간격으로, 상세 미수집 대상은 별도 상태 파일의 성공 여부·스키마 버전으로 판단합니다. 상세 성공 시각은 그 파일의 `lastDetailSuccessAt`에 기록합니다.

- `thumbnailUrl`: 썸네일 URL 1개. 별도 썸네일이 없으면 메인 이미지로 보완합니다.
- `imageUrls`: 상품 메인 이미지 URL 배열.
- `descriptionImageUrls`: 상품 설명 이미지 URL 배열.
- 단일 상품의 `sku`: `CHEONYU-93060`, `CCDOME-1000005353` 형식으로 생성합니다.
- 옵션 상품의 상위 `sku`: 빈 문자열 `""`입니다. 각 `options[].sku`에 `CHEONYU-93060-옵션ID`처럼 사이트·상품 ID·옵션 ID를 조합하여 재고 단위별로 생성합니다. 옵션 ID를 확인하지 못하면 임의로 만들지 않고 해당 SKU를 비웁니다.
- `slug`: 현재는 빈 문자열 `""`로 저장합니다.

기존 아카이브도 읽을 때 이 SKU 규칙을 적용하고 다음 저장 때 반영합니다. 상품·옵션의 원본 ID와 재고 수량은 유지합니다. 상세 수집이나 번역 입력에 옵션이 빠져 있어도 기존 옵션 SKU를 보존합니다.

최종 상품은 두 사이트 모두 같은 43개 필드를 사용합니다. 값이 없는 항목은 `null`, 빈 문자열 또는 빈 배열일 수 있으며, 평점·리뷰 수처럼 수집하지 않는 항목은 기본값입니다. 천유 스펙은 소재 등의 속성으로, 과자생각 스펙은 `labelKo`, `labelJa`, `valueKo`, `valueJa` 등의 항목으로 저장됩니다. 과자생각의 주요 스펙 일본어 라벨은 고정 매핑합니다.

## 4. 수집 후 확인 방법

### 실행 상태와 결과 파일

앱의 실행 목록에서 **완료/실패 상태, 수집 수량, 경고 메시지, 저장 폴더**를 먼저 확인합니다. CSV 저장 버튼으로 자료를 확인하거나 결과 폴더의 JSON을 열어봅니다.

실행별 결과는 선택한 저장 폴더 아래 `<사이트>/<실행 ID>/`에 생성됩니다. 기본 저장 폴더는 `C:\Users\사용자명\MallCollector`입니다.

| 파일 | 확인할 내용 |
| --- | --- |
| `result.json` | 이번 실행 대상 상품의 아카이브 병합 결과. 최상위는 상품 객체 **배열**입니다. |
| `inventory.csv` | 천유 옵션별 재고·가격 관측값 또는 과자생각 판매 상태 |
| `summary.csv` | 상품별 재고 상태와 요약 |
| `products.csv` | 목록에서 수집한 상품 정보 |
| `details.csv` | 상세 수집 시 확보한 원본 상세 정보 |
| `detailResult.json` | 이번 실행에서 상세 수집을 시도한 상품의 병합 결과 |
| `result_translated.json` | 상세 수집의 번역 결과. 번역 단계가 성공했을 때 생성됩니다. |
| `debug-*.html` | 사이트 응답을 확인하기 위한 진단 자료. 수집 경로에 따라 생성됩니다. |

한 상품을 골라 다음 항목을 확인하면 됩니다.

1. `id`, `sourceMall`, `nameKo`가 해당 상품과 일치하는지 확인합니다.
2. `originalPrice`, `wholesalePrice`가 위 가격 기준에 맞는지 확인합니다.
3. `thumbnailUrl`, `imageUrls`, `descriptionImageUrls`에 올바른 이미지가 들어갔는지 확인합니다.
4. `saleStatus`, `stockStatus`, `stockQuantity`, `options`를 확인합니다. 신규 천유 상품은 일반 수집만 완료한 시점에 상세 이미지가 아직 비어 있을 수 있습니다. 소비자가는 일반 수집에서도 확인하며, 확인 실패 시 비어 있을 수 있습니다.
5. 가격 누락·상세 실패·번역 실패 경고를 확인합니다. 기존값을 보존한 상품은 최신값인지 추가 확인이 필요합니다.

### 누적 아카이브와 서버 반영

두 사이트의 누적 데이터는 기본적으로 다음 **한 파일**에 저장됩니다. 실행별 `result.json`과 누적 아카이브의 상품 수는 다를 수 있습니다.

```text
C:\Users\사용자명\MallCollector\archive\v앱버전_archive.json
```

기존 데이터에 사이트 정보가 없으면 양의 정수 ID 100,000 이하는 천유, 1,000,000,000 이상은 과자생각으로 식별합니다. 원본 ID는 유지하고 사이트와 ID를 함께 사용해 병합합니다. 기존 파일의 `slug`도 다음 아카이브 저장 때 빈 문자열로 정리됩니다.

아카이브 파일은 `{"cheonyu": [...], "ccdome": [...]}`처럼 쇼핑몰별 배열로 저장합니다. 각 상품의 `sourceMall`과 나머지 필드는 그대로 유지하며, 새로운 쇼핑몰은 해당 `sourceMall` 값으로 배열이 자동 생성됩니다. 천유·과자생각은 상품이 없어도 빈 배열을 저장합니다. 실행별 `result.json`과 서버 전송 데이터는 기존 상품 배열 형식을 유지합니다.

기존 배열·상품 ID 객체 형식도 읽을 수 있습니다. 다음 아카이브 저장 시 기존 파일을 `.before-mall-groups.bak`으로 한 번 백업하고 새 형식으로 변환합니다. 쇼핑몰을 판별할 수 없거나 저장 그룹과 `sourceMall`이 충돌하면 원본을 덮어쓰지 않고 오류를 표시합니다.

서버 반영 여부는 앱의 **전송 내역 → 서버 요청·전송 내역**에서 확인합니다. 실제 요청과 응답은 날짜별 JSON 로그로 남습니다. 파일 저장 성공과 서버 전송 성공을 각각 확인하세요.

### 운송장 계정과 수동 테스트 알림

환경설정의 **운송장 계정**에서 KSE OMS 계정을 등록·수정·삭제하고 사용할 계정을 선택합니다. 비밀번호는 Windows 보안 저장소로 암호화한 `credentials.bin`에 보관하며 화면으로 다시 반환하지 않습니다. 수정할 때 비밀번호를 비워 두면 기존 값을 유지합니다. 선택 계정은 재시작 후에도 유지됩니다.

운송장 수집 중 KSE 로그인 페이지가 열리면 선택한 계정의 ID·PW가 자동 입력됩니다. **로그인 버튼은 직접 누르세요.** 계정 미선택 또는 입력 실패 시 직접 로그인할 수 있습니다. 계정이나 ID·PW를 바꾸면 별도 브라우저 세션을 사용하므로 이전 계정의 로그인 상태를 재사용하지 않습니다.

환경설정의 **서버에 테스트 알림 보내기**는 저장된 서버 설정으로 작은 테스트 이벤트를 한 번 보냅니다. 버튼 아래에 서버 응답 또는 오류를 표시하고 전송 내역에도 기록합니다. 버튼 클릭 없이 자동으로 보내지 않으며, 관리자 문자·메일 발송 기능은 포함하지 않습니다. 서버는 테스트 이벤트를 처리하는 규격을 구현해야 합니다.

환경설정에서 저장한 **서버 API 주소**는 상품·운송장 전송, 장바구니 조회, 수동 테스트에 공통으로 사용합니다. 요청 본문은 압축하지 않은 JSON이며, 각 작업의 기존 본문 형식을 유지합니다. 요청·응답 형식과 수동 테스트 이벤트 처리는 [서버 연동 규격](SERVER_API.md)을 참고하세요.

## 5. 반복 수집 운영

| 목적 | 권장 설정 |
| --- | --- |
| 하루 3회 일반 수집 | 반복 실행, 8시간 간격 |
| 하루 2회 일반 수집 | 반복 실행, 12시간 간격 |
| 주 1회 상세 갱신 | 반복 실행, 1주 간격, `범위 내 전체 상품` |

반복 간격은 최초 실행 시각을 기준으로 계산합니다. 작업이 오래 걸려 놓친 회차는 건너뛰며, 계정 충돌 등으로 시작하지 못하면 1~5분 간격으로 재시도합니다. 일반과 상세를 같은 계정으로 등록하려면 첫 작업이 끝난 후 다른 반복 작업을 추가합니다. 이후 예약끼리 겹치는 경우에는 재시도가 적용됩니다.

앱을 계속 켜 두어야 하며 **앱 재시작·화면 새로고침 후 반복 예약은 자동 복원되지 않습니다.** PC 절전 중에는 실행되지 않습니다. 결과·로그 파일도 계속 쌓이므로 저장 공간을 주기적으로 확인하세요. 전체 상세 갱신 범위가 20페이지를 넘으면 작업을 나누어 설정해야 합니다.

# 크롤링 프로그램 설치·실행 차단 시 조치 안내

본 프로그램은 회사 내부 업무용으로 제작된 Windows 데스크톱 프로그램입니다.

## 1. 설치 파일 실행 시 `Windows의 PC 보호`가 표시되는 경우

## 2. Windows 보안의 보호 기록 확인

1. Windows 시작 메뉴에서 `Windows 보안`을 검색해 실행합니다.

## 6. `spawn UNKNOWN` 오류가 표시되는 경우

다음 오류는 프로그램 내부 실행 파일이 Windows 보안 또는 사내 백신에 의해 삭제·격리·차단됐을 때 발생할 수 있습니다.

```text
Error: spawn UNKNOWN
```

다음 순서로 조치합니다.

1. Windows 보안의 `보호 기록`을 확인합니다.
2. 프로그램 관련 파일이 차단 또는 격리됐는지 확인합니다.
3. 회사에서 전달받은 정식 파일이 맞다면 허용 또는 복원합니다.
4. 이미 파일이 삭제된 경우 기존 프로그램을 제거합니다.
5. 설치 파일을 다시 전달받습니다.
6. 설치 파일 속성에서 `차단 해제`를 적용합니다.
7. 프로그램을 다시 설치하고 실행합니다.

허용 처리 후에도 동일한 오류가 발생하면, 이미 삭제된 파일이 복원되지 않은 상태일 수 있으므로 반드시 재설치해야 합니다.
